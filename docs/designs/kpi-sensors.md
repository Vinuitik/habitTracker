# KPI sensors: seamless KPI collection on the user's own devices

Status: DRAFT (2026-11-03). It extends `kpi-tracking-agent.md`, and where they disagree this doc wins.

## Goal
The user describes a KPI ("YouTube time", "coding hours", "LeetCode rank", "push-ups"). The agent picks the most seamless source that fits the user's budget, builds the collector, proves it works, and only then turns it on. The user stops copying numbers by hand.

## Grand vision (every prototype must fit this pipeline)
```
TALK      chat with the AI consultant → it proposes a proxy, or a SET of proxies, for the KPI
BUILD     it pulls a technical solution into its harness and writes the collectors
PACKAGE   each collector becomes a deployable program for each target the user wants
          (SERVER sandbox · RUNNER on Linux, then Windows · ANDROID), so one KPI can span several
CONTRACT  the data-access contract is negotiated with the user ONCE, then enforced by the runtime
          and checked statically
COLLECT   readings from all of the KPI's proxies → fused estimate (weights learned from confirmations)
FORECAST  TimesFM (Google's time-series foundation model) predicts the KPI's trajectory
```
Rules that follow from this:
- **Approval is per contract, not per code version.** A contract is the set of sources, paths, hosts and targets. A repair that stays inside the contract and passes the test pipeline deploys without asking again. A repair that widens the contract needs a new negotiation. The sandbox is what makes this safe, because the runtime enforces the contract whatever the code does.
- **A KPI owns N proxies.** Each proxy has its own confidence. The fused value is a weighted average, and the weights update from confirm-inbox answers.
- **Forecasting runs on the user's runner**, not the server. That follows the Relay rule that the server spends nothing. TimesFM is a few hundred million parameters and runs on CPU. It needs a few weeks of history before forecasts mean much, so the UI shows "Forecast after N more days" until then. [NOT IMPLEMENTED]

## Source ladder (the agent climbs down until something fits)
1. **API or public page.** Collected from the SERVER platform, which already exists (sandbox + egress allowlist + encrypted secrets).
2. **An app the user already runs, with local data.** Collected on the RUNNER platform. This covers ActivityWatch, browser history and app SQLite files.
3. **The agent writes its own collector over raw local data.** Also on RUNNER.
4. **Install an app or service.** Only when `budget > 0`, or when it's free. The agent says what to install, then wraps it with rung 1 or 2.
5. **Ask on done.** When the habit is marked done, a prompt asks "how many?". This is the fallback for push-ups, weight and similar.
6. Phone sensors: the ANDROID app. [NOT IMPLEMENTED, last phase]

Budget is set at intake:
- **0:** no paid apps or APIs; the agent may build its own collector.
- **Free:** free installs are allowed.
- **A number:** that's the monthly ceiling. The agent states the cost.

## The RUNNER platform: core design

### Collectors are pure functions over snapshots
A collector never touches the live system. The runner prepares its **inputs**, then runs it with the network off:

```
runner scheduler (or a dry-run)
  → sources produce inputs, read-only, in a temp dir:
      activitywatch: the runner queries localhost:5600 for buckets/events in [from, to) → aw.json
      file:<glob>:   the runner copies the declared files (copying beats locked browser SQLite) → files/
  → bwrap sandbox: --unshare-all (no network), ro-bind the inputs dir, tmpfs $HOME, no host fs
      python3 collector.py --from F --to T --inputs /in
  → stdout {value, unit, evidence: [≤20 rows explaining the number]}
  → stored in the runner's local readings store
```

Why this shape:
- **Safe.** There is no network and no host filesystem. The collector can't leak or damage anything.
- **Testable.** A fixture test is just inputs in and a number out.
- **Catches up.** Runs are parameterised by `--from/--to`, so after the laptop sleeps, the runner backfills the missed windows.

**Rule:** a RUNNER collector never has network access. A KPI that needs the internet is a SERVER capability, and that platform already has an egress allowlist.

Limits: `systemd-run --user --scope` with MemoryMax=128M, CPUQuota=25%, RuntimeMaxSec=60. There's a fallback for systems without systemd.

### Collector bundle (generated by the runner "kpi" job)
```
manifest.json  { id, kpiName, version, schedule ("hourly"|"daily HH:MM"), window ("1d"),
                 sources: [{type:"activitywatch", buckets:["window","web"]} | {type:"file", glob, why}],
                 unit, aggregation ("sum"|"last"|"max") }
collector.py   stdlib only
fixtures/      inputs + expected.json (≥2 cases, incl. an empty day → 0)
```

### Approval binds to a contract
1. The user approves the **contract** in the web UI (the /relay pages are 2FA-gated). The contract is the manifest's `sources`, `targets` and schedule, shown in plain language, for example "Reads ActivityWatch window and browser history · no internet · runs hourly". The dry-run result is shown alongside.
2. The runner stores `sha256(contract)` as approved.
3. A new code version runs only if its manifest's contract hash matches and it passed pipeline steps 2–4.
4. A wider contract needs a new approval.

Threat model:
- **Compromised hub:** it can ship new code inside an approved contract. That code still sees only the declared snapshots, with no network, so the worst case is a wrong number, not a leak.
- **Widening the contract:** that always needs the user.

### Readings flow: the hub pulls
The hub's `RunnerCollectorProvider` calls `GET /v1/collectors/{id}/readings?since=` through `RunnerClient`, both nightly and when the runner comes online. The result goes into `KPIService.addKPIDataForUser`.
- No uplink protocol change is needed.
- If the runner is offline, readings wait locally.
- This replaces the old design's Drive-mailbox channel for device data.

## Test pipeline: nothing reaches ACTIVE untested
```
1. GENERATE  runner kpi job → bundle
2. STATIC    hub: manifest schema, stdlib-only imports, declared globs are not secret paths
             (reuse the job deny-list: .ssh, .env*, keyrings, browser cookie/password DBs)
3. FIXTURES  server sandbox runs collector.py on fixtures/ (no device needed); must match expected.json
4. DRY RUN   the runner runs it once on real snapshots → value + evidence
5. CONFIRM   the user sees "Yesterday: 47 min YouTube" + evidence rows → "Looks right" / "Wrong, because…"
             "Wrong" → repair job with the user's reason, then back to 1 (max 3 rounds)
6. SHADOW    7 days: readings stored as unconfirmed, sampled in the existing confirm-inbox (M3);
             plausibility guard vs. history (> 5× median or impossible values → flag)
7. ACTIVE    existing circuit breaker + repair (M12) apply; a repaired bundle restarts at 2
```
Steps 5 and 6 also apply to SERVER capabilities. This closes the "believable wrong number" gap found in the play-test.

## Phases and milestones
Each milestone is one agent and one commit. Phases are sequential unless noted.

- **S0: Range test** (no code, with the user). About 10 KPIs across the ladder. The output is a table of works / plausible-but-wrong / missing, and it can re-order S4–S7. *Parallel with S1.*
- **S1: Confirm gate + plausibility** (hub). Pipeline steps 5–6 for the existing SERVER platform. Evidence comes from capability stdout, so SERVER scripts also emit `evidence`.
- **S2: Runner collector engine** (Relay repo, Go). This covers:
  - `internal/collectors`: manifest parse, the activitywatch and file sources, bwrap exec + limits, scheduler with backfill, local readings store.
  - API: `POST /v1/collectors` (install pending), `POST .../{id}/approve {sha256}`, `POST .../{id}/dry-run`, `GET .../{id}/readings?since=`, `DELETE .../{id}`, `GET /v1/collectors`.
  - Go tests, including a sandbox escape test (network, a host path, writing outside tmp → all refused).
- **S3: Hub RUNNER platform.**
  - `CapabilityPlatform.RUNNER`, generation prompt → bundle + fixtures.
  - Pipeline steps 2–4, `RunnerCollectorProvider` pull.
  - Approve and dry-run in the existing live-steps UI (plain language, no JSON).
- **S4: Conversational intake + budget + ladder.** Multi-turn, using the planner clarify pattern. The agent states which rung it chose and why.
- **S5: Ask-on-done quantity** (habit completion prompt → KPI value).
- **S6: Composite and classified KPIs.** For example, "learning time" = window titles and URLs classified by an AI job into categories. The classification rules get frozen into the collector, so there's no AI call per run.
- **S7: Android app** (Health Connect + UsageStats primitives, AccessibilityService fallback). Its own design pass comes first.

## RUNNER sandbox per OS
All three share one contract: no network, read-only declared inputs, a scratch dir, and CPU/memory/time caps.

| OS | Sandbox | Notes |
|----|---------|-------|
| Linux | `bwrap --unshare-all` + `systemd-run --user` limits | Verified 2026-11-03 on Ubuntu with `apparmor_restrict_unprivileged_userns=1` (the stock bwrap profile allows it) |
| Windows | **AppContainer** (LPAC, no capabilities = no network) + Job Object limits; the runner ships embedded Python with an ACL granting it to the AppContainer SID | Works on Home. Prototype fallback: WSL2 + bwrap (same as Linux). Windows Sandbox was rejected: Pro only, ~10–20s start, one at a time. [NOT IMPLEMENTED] |
| macOS | `sandbox-exec` (Seatbelt) profile: deny network, allow-read of the inputs dir only | macOS is Darwin/BSD, not Linux, so bwrap doesn't exist there. Seatbelt is deprecated but still what Chrome uses. [NOT IMPLEMENTED] |

## Prototype 1: "YouTube time" on Windows (do this before any S-milestone code)
It proves three things: (a) the AI writes a collector that gives a correct number, (b) the "pure function over a snapshot" shape holds, (c) a sandbox runs Python on Windows with the network blocked.

Steps are run on the Windows machine. Its Relay runner's Claude can do them from the prompt in `kpi-proto-windows-prompt.md`.
1. Install ActivityWatch, plus its browser extension for the browser you actually use. Use the PC normally for 1 day.
2. Snapshot: export the window and web buckets for one day from `localhost:5600` → `aw.json`.
3. The AI writes `collector.py` (stdlib only, `--inputs --from --to` → `{value, unit, evidence}`) plus 2 fixtures. It runs the fixtures.
4. Run it sandboxed:
   - **Option A:** WSL2 + bwrap, if WSL exists.
   - **Option B:** an AppContainer launcher spike, a small Go or Python + pywin32 program.
   - **Fallback:** run it unsandboxed, but record that it was unsandboxed.
5. Write down the number, the top evidence rows, and your own estimate. That goes in a results section here.

Success means the number is within about 15% of your estimate, the evidence explains it, and a network call made inside the sandbox fails.

## Technology Notes
- **bwrap** needs unprivileged user namespaces. Ubuntu 24+ restricts them via AppArmor (`kernel.apparmor_restrict_unprivileged_userns`), so the runner may need an AppArmor profile for bwrap. Check this in S2 first.
- **ActivityWatch** must be installed and running. Its API is unauthenticated on localhost, which means any local process can read it. That's acceptable, because it's the user's own machine. If it isn't running, the source fails and the run is retried. It does not count as a collector failure.
- **Snapshots copy files.** A large browser history (~100MB) copied hourly costs I/O. Declared globs are size-capped at 200MB per run.
- **The readings store** is local to the runner (a file). If the runner's data dir is wiped, unpulled readings are lost. The hub pulls at least daily.
- **Approval hashes** live in the runner's data dir. Wiping it means re-approving every collector, which is fail-safe.
